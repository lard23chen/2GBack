code3 模組系統規格文件

文件目的 本文件整理 D:\2025\AI\2GBack 資料夾下所有與 code3（品牌代碼管理）相關的 9 個 Classic ASP 程式。 code3 是 code1／code2 模組再往下一層的資料，命名與程式風格延續同一系列，但實作完整度明顯低於 code1、code2—— 少了好幾項在兄弟模組中存在的防呆檢查，且其中一個處理器檔案經比對後被確認是「寫好了但沒有任何頁面會呼叫到」的孤兒程式。 這些落差都已在文中明確標出，供 AI／工程師改寫成其他程式語言時判斷要不要在新系統中補回這些規則。

本文件已修正的前次誤判 在 code1／code2 規格文件的初版中，曾將「組字串用大寫變數 SQL、執行查詢卻寫小寫 sql」誤判為程式缺陷。 經確認 Classic ASP／VBScript 的變數名稱不分大小寫，SQL 與 sql 其實是同一個變數，並非缺陷。 code1、code2 的規格文件已同步更正；本文件（code3）在遇到相同寫法時，直接註明為「非缺陷」，不再重複誤判。

1. 模組概觀

此模組中文名稱為「品牌管理」，管理的是「品牌代碼（Code3）」——是 code2 模組「服務代碼（Code2）」底下的次一層分類， 也是目前所知代碼分層架構的第三層：

TB_GD_RepairCode1_200501（項目, Code1） └─ TB_GD_RepairCode2_200501（服務, Code2, FK→Code1） └─ TB_GD_RepairCode3_200501（品牌, Code3, FK→Code1, FK→Code2) ← 本模組管理的對象 └─ TB_GD_RepairDataList_200501（商品/明細, FK→Code1,Code2,Code3) ← 只被本模組引用做「停用前檢查」，其 CRUD 邏輯不在此資料夾

每一筆品牌代碼（Code3）同時關聯到 code1 與 code2 兩個外鍵（不像 code2 只需要一個 code1 外鍵）， 且查詢/編輯/暫停訊息等操作，都需要確認整條父鏈（Code1 與 Code2）都必須是啟用中才能進行，比 code2 模組多一層檢查。

功能設計上延續 code1／code2 的四大操作：列表查詢、新增、編輯／停用、暫停服務公告，但實作深度不對稱：

  • 新增（code3add_db.asp）完全沒有重複代碼檢查，也沒有 code2 模組那種「99互斥」的伺服端驗證（只有前端確認對話框，沒有後端規則）。
  • 編輯（code3mod.asp）沒有重複代碼檢查，也沒有租戶／父層範圍限制——只用 Code3 這個 PK 去 UPDATE，語意上比 code1mod.asp／code2mod.asp 弱得多。
  • 另外存在一個 從未被任何頁面連結或表單指向的孤兒檔案 code3mod_db.asp，裡面反而寫了一條「父層服務必須啟用才能編輯品牌」的檢查，但因為沒有任何東西會呼叫它，這條規則實際上從未被執行。

4. 架構重點

雙資料庫連線
conn：操作 TB_GD_RepairCode1_200501、TB_GD_RepairCode2_200501、TB_GD_RepairCode3_200501、TB_GD_RepairDataList_200501（皆為租戶資料）。conn0：操作 TB_GD_StopServiceMSG_201010、TB_GD_StopServiceMsgLOG_201010（共用／公告資料）。與 code1、code2 模組同一套雙連線慣例。
雙外鍵、雙層父鏈檢查
TB_GD_RepairCode3_200501 同時持有 code1 與 code2 兩個外鍵。查詢／編輯／暫停訊息頁面組 SQL 時固定三表 join（a=Code3, b=Code2, c=Code1），並要求 b.use_flag=0 and c.use_flag=0——也就是祖父層（項目）與父層（服務）都必須啟用中，比 code2 模組（只需檢查單一父層）多一層。
雙重導覽路徑模式（flag 參數，code3 特有）
code3.asp 內部依 request("flag")="0" 與否，切換兩套完全不同的連結／表單路徑：
・flag="0"：表單 action 用 ../../../../system/rightmain.asp（多一層 ../），其餘連結（新增/修改/停用/下拉連動）皆用相對於當前目錄的檔名（不加 Session("folder") 前綴）。
・flag 為其他值（含未帶此參數）：表單 action 用 ../system/rightmain.asp，其餘連結都加上 Session("folder") 前綴。
這代表 code3.asp 被設計成可以從兩個不同的目錄深度／選單入口掛載，但 code1.asp／code2.asp 完全沒有這種機制，只用固定路徑。改寫時必須先搞清楚實際上線環境是否真的用到 flag=0 這條路徑（例如另一個選單樹或子系統的入口），否則新系統可能會漏掉一種合法的進入方式。
導覽狀態
沿用 code1／code2 模組同一套 Session("folder")、Session("url")／Session("URL")、Session("Cname")。
狀態機（Use_flag）
Code3 本身：0=啟用、1=停用（與 code1、code2 相同語意）。但下一層 TB_GD_RepairDataList_200501 的停用前檢查用的是 Use_flag<>1（「不等於1」，而非「等於0」），暗示商品明細層的 Use_flag 可能存在第三種值（呼應 code2／code3 暫停訊息畫面上出現的「2=待上架」選項，見 code2 規格文件 D2-11）。

8. 商業規則彙整（改寫時的核心行為清單）

  1. 租戶隔離（間接、且不完整）：Code3 本身無 groupid，租戶範圍需透過 join 到 Code1 取得；但實際在用的編輯處理器 code3mod.asp 完全沒有做這個檢查（見 D3-05），是本模組最大的規則缺口。
  2. 雙層父鏈必須啟用：列表查詢、編輯、暫停訊息設定，都要求所屬 Code1（項目）與 Code2（服務）都必須 use_flag=0；任一層被停用，都會擋住品牌的編輯與暫停訊息設定（但同 D3-06 所述，擋法有缺陷：只顯示警告不會真的中止）。
  3. 停用品牌不檢查父鏈狀態：code3mod_stop.asp 本身沒有檢查 Code1／Code2 是否啟用，只檢查下層商品明細，與 code2 模組「停用不檢查父層」的不對稱設計一致。
  4. Use_flag 語意：Code3 本身 0=啟用、1=停用；但下一層商品明細用 Use_flag<>1 判斷「非停用」，語意上比單純二元判斷更寬鬆（可能允許某種第三態，如「待上架」）。
  5. 編輯僅限未啟用品牌；停用僅限啟用中品牌：與 code1、code2 模組相同的互斥顯示規則（僅列表頁 UI 層面）。
  6. 新增時無重複代碼檢查（本模組特有的缺口）：與 code1、code2 模組明確禁止「同範圍內重複啟用中代碼」不同，code3 的新增（code3add_db.asp）沒有實作對等的檢查。若改寫時要與 code1／code2 行為一致，需要額外補上。
  7. 編輯時無重複代碼檢查（本模組特有的缺口）：同上，code3mod.asp 也沒有實作。
  8. 品牌編號 "99" 目前只是前端提示，非強制規則：與 code2 模組「99 與其他啟用中代碼互斥」的伺服端強制規則不同，code3 只有前端 confirm() 對話框告知「品牌編號99於前台不顯示」，使用者仍可直接送出，沒有任何伺服端阻擋機制。
  9. 停用前檢查下一層：停用 Code3 前必須確認底下沒有「非停用」的商品明細（TB_GD_RepairDataList_200501.Use_flag<>1），否則拒絕（與 code1／code2 模組「停用前檢查下一層」規則同構）。
  10. 暫停公告固定層級：本模組建立/編輯的暫停公告固定 Code4='0'，LinkLevel=2（品牌層級）。
  11. 暫停公告日期慣例與時間合理性檢查：與 code1、code2 模組完全相同。
