佣金管理模組系統規格文件

Classic ASP 逆向解析 ｜ 檔案群：*Commission*.asp（8 支）｜ 版本：v1.1 ｜ 日期：2026-07-30

1. 模組概觀

佣金管理模組負責設定每張票券商品（TB_ALEX_MainTicket_200604）的 銷售計價方式、經銷商佣金拆帳（0~12 梯次）、手續費計算方式、退票退款設定， 並同步管理電影類別商品（TB_CHRIS_MovieDataList_200603）的相同資訊。

模組分為兩個平行子系統：

  • ERA 票務佣金：針對 TB_ALEX_MainTicket_200604（票券/活動類商品），透過 All_ERACommission_Manage → Mod_TicketCommission 進行設定。
  • Movie 電影佣金：針對 TB_CHRIS_MovieDataList_200603（電影類商品，actionid 固定為 "0630"），透過 All_MovieCommission_Manage → Mod_MovieCommission（POST 到同一個 Mod_TicketCommission_db）進行設定。
⚠ 兩個子系統共用同一個寫入 Handler：
Mod_TicketCommission_db.asp 同時處理 ERA 票務佣金與 Movie 電影佣金的寫入（由傳入的 actionid 區分）。 Movie 的 Select_TicketCommission.asp 也是以 actionid="0630" 連接相同的 db 頁面。

4.2 銷售佣金表 TB_ALEX_TicketCashData_200603

每筆商品（pdid）可有 0~12 個梯次（sales_count），每梯次一列。

欄位說明
pdid商品 PK（FK → MainTicket）
actionid票務系統 actionid
sales_count梯次序號（0~12）
sales_code銷售代碼（syscodeid，對應某個速碼系統）
factory_broker廠商佣金（原廠抽成）
handy_broker超商/代理佣金
our_broker我方佣金（安心抽成）

⚠ 寫入方式為 DELETE + INSERT（非 UPSERT）：
每次儲存時對有傳入 sales_code 的梯次執行 DELETE FROM TicketCashData WHERE pdid=? AND sales_count=? 再 INSERT，無交易保護。若中途錯誤可能造成部分梯次資料遺失。

6. 商業規則

6.1 U_Flag 與操作入口決策

查詢 TB_ALEX_Session_200604 該商品是否有 use_flag IN (0,2,3) 的場次：

U_Flag意義ERA Manage_2 按鈕
1（eof）無有效場次（已下架）「修改佣金」→ Mod_TicketCommission（可編輯）
0（有 use_flag=0 場次）上架中「查看詳情」→ Show_TicketCommission（唯讀）
2待上架同上
3待確認同上；Show 頁顯示「退費設定」且 title="設定"
4待設定同上；Show 頁顯示「退費設定」且 title="設定"
注意：ERA Manage_2 的 flag=0 路徑（相對路徑）與 flag≠0 路徑（Session folder 前綴）在 U_Flag=0 時都指向 SHOW_ERA_Ticket.asp， 但 U_Flag=1 時 flag≠0 也指向 Mod_TicketCommission（兩路徑一致），推測 flag 參數控制的是路徑前綴而非業務邏輯。

6.2 銷售類型 (sales_type)

值說明
1一般商品 / 代理商品；商品代碼由系統決定
2代售商品；需輸入 BrevityCode（速碼，3碼）；UI 上有 chkbc() JavaScript 驗證函式，根據速碼自動填入各梯次的 Syscode 欄位

6.3 經銷商佣金層 GetBroker（0~12 梯次）

佣金設定支援 0~12 梯次（對應不同銷售張數層級）。Mod_TicketCommission（設定頁）用 GetBroker 迴圈渲染 0~12 梯次；Show_TicketCommission（唯讀頁）只顯示梯次 1~8，用硬編碼 rs_cash1~rs_cash8 各自查詢，非 GetBroker。 每個梯次呼叫 GetBroker(梯次, Syscode, first, pdid, actionid, ...) 取得：

  • syscodeid：銷售代碼 ID（hidden，寫入時用）
  • syscode：顯示用速碼（text input，可輸入）
  • syscodename：速碼對應名稱（readonly）
  • factory_broker：廠商佣金算法（select，值域來自 TB_GD_systemCode_200501 codetype='COMMISSION'）
  • handy_broker：超商佣金算法（同上）
  • our_broker：我方（安源）佣金算法（同上）

Show 頁的速碼下拉（salescode_n）值域來自 TB_GD_systemCode_200501 codetype='COLLECTION'（codeid=速碼 ID，syscodename=速碼名稱）。

GetBroker 為外部 Sub/Function，定義位置未在這 8 支檔案中，推測在某個 include 檔案中（如 func_Commission.asp 或類似）。 改寫時需找到其實際 SQL 邏輯：應查詢 TB_ALEX_TicketCashData_200603 by pdid + sales_count， 並關聯速碼主表取得 syscode / syscodename。
Show 頁不依賴 GetBroker：直接用 TB_GD_systemCode_200501 取下拉選單，rs_cash{n} 取已存的 sales_code/factory_broker/handy_broker/our_broker 值來 pre-select。

寫入驗證規則（Mod_TicketCommission_db）

  • 若 sales_code≠""（梯次有效）：驗證 factory_broker / handy_broker / our_broker 三者非空，任一空 → alert「{x}張未選擇XXX佣金!」+ history.go(-1)；flagcode=1，累積 DELETE+INSERT sql 字串
  • 若 sales_code="" → alert「上架商品代號不可空白!」+ history.go(-1) + response.end（注意：v1.0 說的「新增商品代碼不可為空白」為誤，以原始碼為準）
  • ⚠ factory_broker 驗證失敗時 response.end 被 comment out，僅 handy_broker / our_broker 的 response.end 有效；factory_broker 空白時 ASP 端會繼續執行
  • 以上驗證通過後 flagcode=1；只有 flagcode=1 時才執行 MainTicket UPDATE 與 TicketCashData DELETE+INSERT

6.4 計價方式 (valuation_type / fixed_money / fixed_unit)

⚠ v1.0 推測錯誤（已修正）：原推測 1=固定金額，現由 Show_TicketCommission.asp UI 邏輯確認：1=變動售價，2=固定售價。
欄位說明
valuation_type1=變動售價（動態定價，無固定金額）；2=固定售價（需填 fixed_money + fixed_unit；fixed_money < 999999）
fixed_money固定計價金額（varchar，maxlength=6）；僅 valuation_type=2 時有意義
fixed_unit計價單位（int，FK → TB_GD_UnitCode_200501.unitid）；查詢用 conn（非 conn3）

6.5 手續費計算方式 (procedures_type)

procedures_type 值說明對 TicketFeeData 的影響
1內含（無附加手續費）不寫入 TicketFeeData（也不清除既有資料）
2外加（逐梯次設定附加費）對每個 sales_code≠"" 的梯次：DELETE + INSERT TicketFeeData（fee_count = 梯次序號，extra_fee = 輸入值）；extra_fee 為必填否則 alert 警告
⚠ procedures_unit 欄位已棄用（推測）：
Mod_TicketCommission_db.asp 中有 'sqlmain= sqlmain & " procedures_unit =" & procedures_unit & ", " 被 comment out， 改寫時此欄位可忽略或保留歷史相容。

6.6 退票/退款設定 (refund_type / payback_type)

寫入時優先執行（不依賴 flagcode）：

UPDATE TB_ALEX_RefundTicket_201106
SET refund_type = ?, payback_type = ?
WHERE pcode_in = ?

pcode_in 從 Request 取得（由 Mod_TicketCommission 頁面傳送），對應 ERA 商品管理新增時預佔的序號記錄。 refund_type / payback_type 的具體值域未在此程式中說明，推測由退費設定子系統（Show_SetRefund / Mod_ERA_Return）另外維護。

6.7 commissionsetting 狀態旗標

TB_ALEX_MainTicket_200604.commissionsetting 是工作流狀態旗標， 佣金管理設定完成後強制更新為 0： 

sqlmain = sqlmain & " commissionsetting = 0 "

初始值（新增商品時）推測為非 0（如 1 或 NULL），代表「佣金尚未設定」； ERA 商品管理列表（All_ERACommission_Manage_2）顯示 rs("commissionsetting") 欄位值（但被 comment out 未渲染）。 改寫時此欄位應整合進工作流狀態機。

6.8 電影佣金（Movie）特殊子系統

  • 固定 actionid="0630"：所有 Movie 商品的 actionid 都是 "0630"，硬編碼在 All_MovieCommission_Manage 查詢與 Select_TicketCommission → hidden input。
  • 不同主表：查詢 TB_CHRIS_MovieDataList_200603（不是 MainTicket），但佣金寫入時用的仍是 pdid + TicketCashData，共用 Mod_TicketCommission_db。
  • 商品欄位不同：顯示 showdate/showtime/seat/showareaid（劇院）取代 programname/startpresaledate 等票務欄位。
  • 列表篩選：All_MovieCommission_Manage 固定 code1=45 查詢 code2（硬編碼，對應電影的 code1 分類值）。
  • pcode_out：Movie 商品有 pcode_out（出貨碼），是 ERA 商品沒有的欄位。

7.5 Mod_TicketCommission_db.asp Handler

用途：ERA + Movie 共用的佣金寫入 Handler。

執行步驟（依序）

  1. 讀取所有 Request 參數：pdid、item_5、sales_type、valuation_type、fixed_money、fixed_unit、procedures_type、refund_type、payback_type、pcode_in、begin_date、end_date、actionid
  2. UPDATE RefundTicket（無論 flagcode）：
    UPDATE TB_ALEX_RefundTicket_201106 SET refund_type=?, payback_type=? WHERE pcode_in=?
  3. for x=0 to 12（13 個梯次）：
    • 讀 sales_code{x}（注意：factory_broker / handy_broker / our_broker 三者均固定讀 _0 後綴，可能為 bug）
    • 若 sales_code≠""：驗證 factory_broker/handy_broker/our_broker 非空 → 組合 sql（DELETE + INSERT TicketCashData）; flagcode=1
    • 若 sales_code=""：alert + history.go(-1)
  4. if procedures_type=2：for y=0 to 12 讀 extra_money_{y} → DELETE + INSERT TicketFeeData
  5. if flagcode=1：
    UPDATE TB_ALEX_MainTicket_200604 SET Sales_type=?, procedures_type=?, valuation_type=?, fixed_money=?, fixed_unit=?, commissionsetting=0 WHERE pdid=?
    然後執行前面組合的 sql（TicketCashData DELETE+INSERT）
  6. 成功：alert + location.href=Mod_TicketCommission.asp?flag=0&pdid=?&mid=?&actionid=?（self-reload）
⚠ Bug：梯次 broker 欄位讀取固定取 _0 後綴
factory_broker = Request("factory_broker_0")
handy_broker = Request("handy_broker_0")
our_broker = Request("our_broker_0")
在 for x=0 to 12 迴圈中，三者的 Request key 都固定用 _0，未依 x 變化。 這意味著梯次 1~12 的 factory_broker/handy_broker/our_broker 均取用梯次 0 的值，所有梯次的佣金比率實際上都相同（取梯次 0 的值）。 這很可能是 bug（原本應該是 Request("factory_broker_" & x)）。

8. 已知缺陷與注意事項

#位置問題描述風險
1Mod_TicketCommission_db梯次 broker 值固定讀 _0：factory_broker/handy_broker/our_broker 在 for 迴圈中固定讀 Request("XXX_0")，導致梯次 1~12 的佣金與梯次 0 相同🔴 高（資料邏輯錯誤）
2所有 SQLSQL 拼接無參數化，存在 SQL Injection 風險（pdid、pcode_in 等直接拼入）🔴 高

8GetBroker函式定義位置不在這 8 支檔案中，為外部黑箱；改寫時需確認其完整 SQL 邏輯🟠 中（需確認）

9. 改寫建議

  • 修正 Bug #1（最優先）：將 Request("factory_broker_0") 等改為 Request("factory_broker_" & x)，並確認前端表單的 name 屬性對應修正。
  • UPSERT 替代 DELETE+INSERT：對 TicketCashData 與 TicketFeeData 使用 MERGE（SQL Server）或 Upsert pattern，搭配交易（BEGIN TRAN / COMMIT / ROLLBACK）確保原子性。
  • 參數化查詢：所有 SQL 改用 parameterized query，根除 SQL Injection。
  • GetBroker 封裝：找到原始 GetBroker 邏輯後，改寫為 Repository 方法（GetCommissionBroker(pdid, salesCount)），單一責任原則。
  • ERA / Movie 統一介面：兩個子系統共用一個 Handler，建議在 Service 層以 ProductType enum（Ticket / Movie）做策略模式分支，而非以 actionid 隱性決定。
  • commissionsetting 整合工作流：將 commissionsetting 整合進商品狀態機（與 ERA 商品管理的 use_flag 統一管理），避免多個旗標各自散落。
  • refund_type / payback_type 同交易：RefundTicket UPDATE 應納入佣金設定的同一交易中，避免佣金驗證失敗但退票設定已被修改。
  • 電影 code1=45 去硬編碼：從設定檔或資料庫取得電影的 code1 值，不硬編碼。
