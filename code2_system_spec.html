code2 模組系統規格文件

文件目的 本文件整理 D:\2025\AI\2GBack 資料夾下所有與 code2（服務代碼管理）相關的 8 個 Classic ASP 程式， 結構與命名習慣都與同資料夾的 code1（項目代碼管理）模組 高度相似——code2 是 code1 底下的下一層資料。 本文件延續 code1_system_spec.html 的整理方式，但內容完全自足（不需要對照 code1 文件也能看懂 code2 的行為）， 供 AI／工程師在改寫成其他程式語言時直接使用。code2 特有的資料關聯、業務規則與程式缺陷，皆在文中明確標出。

1. 模組概觀

此模組中文名稱為「服務管理」，管理的是「服務代碼（Code2）」——是 code1 模組「項目代碼（Code1）」底下的次一層分類。 整體代碼分層架構為：

TB_GD_RepairCode1_200501（項目, Code1） └─ TB_GD_RepairCode2_200501（服務, Code2, FK→Code1） ← 本模組管理的對象 └─ TB_GD_RepairCode3_200501（品牌, Code3, FK→Code2) ← 只被本模組引用做「停用前檢查」，其 CRUD 邏輯不在此資料夾

每一筆服務代碼（Code2）：

  • 必須歸屬於一個已存在、且「使用中」（use_flag=0）的 項目（Code1），透過欄位 code1 建立關聯。
  • 不直接儲存 groupid／actionid，這兩者都是透過關聯到的 Code1 記錄取得（即：查詢/驗證時常需要 TB_GD_RepairCode2_200501 與 TB_GD_RepairCode1_200501 做 join）。

功能與 code1 對稱：分頁查詢列表、新增服務、編輯服務（僅限尚未啟用）、停用已啟用的服務（需檢查下一層「品牌代碼 Code3」是否仍啟用中）、 以及針對單一服務設定「暫停服務公告訊息」。此外 code2 多了一個 code1 沒有的特殊規則：服務編號 "99" 的互斥規則（見第 8 章）。

4. 架構重點

雙資料庫連線
conn：操作 TB_GD_RepairCode1_200501、TB_GD_RepairCode2_200501、TB_GD_RepairCode3_200501（皆為租戶資料）。conn0：操作 TB_GD_StopServiceMSG_201010、TB_GD_StopServiceMsgLOG_201010（共用／公告資料）。與 code1 模組使用同一套雙連線慣例。
沒有獨立 groupid
TB_GD_RepairCode2_200501 資料表本身沒有 groupid 或 actionid 欄位，所有租戶隔離都是透過 join 到 TB_GD_RepairCode1_200501.groupid 間接完成。改寫時務必透過關聯查詢取得租戶範圍，不能只查 Code2 表本身。
父層必須啟用
幾乎所有 code2 的查詢／編輯／暫停訊息頁面都要求所屬的 Code1（項目）必須是 use_flag=0（啟用中）才能操作；若父項目被停用，服務層的編輯/暫停訊息功能會被鎖住（見第 9 章 D2-08 的例外處理缺陷）。
導覽狀態
沿用 code1 模組同一套 Session("folder")（連結前綴）、Session("url")／Session("URL")（寫入完成後導回頁）、Session("Cname")（稽核用登入者名稱）。
狀態機（Use_flag）
0 = 使用中／啟用，1 = 未啟用／停用（與 code1 相同語意）。但 code2stopmsg.asp 的畫面上出現第三個值 2=「待上架」（disabled，僅顯示不可選），實際資料庫欄位是否真的會出現 2 未經其他檔案佐證，改寫前建議跟後端資料確認，見 D2-11。

6. 資料模型

6.1 資料表一覽

名稱連線性質本模組操作方式
TB_GD_RepairCode1_200501conn父層（項目代碼），詳見 code1 模組文件僅 SELECT（join 取得 groupid/actionid/item1_name，及驗證父項目是否啟用中）

TB_GD_StopServiceMsgLOG_201010conn0暫停公告異動記錄程式碼存在但實際寫入被註解，目前未執行（與 code1 模組相同缺陷）

6.2 欄位明細

TB_GD_RepairCode2_200501（服務代碼主檔）

欄位型態(推測)說明
Code2int, PK系統自動編號，供 TB_GD_RepairCode3_200501.code2 及暫停公告表的 Code2 欄位關聯
code1int, FK所屬項目（→ TB_GD_RepairCode1_200501.Code1），新增時由下拉選單選定，之後不可更改（編輯/停用頁面都沒有讓使用者改變所屬項目的欄位）
Item_2varchar(2)使用者自訂服務編號，前端 maxlength=2；特殊值 "99" 有互斥規則（見 8.5 節）
Item2_namevarchar(15)服務名稱，前端 maxlength=15，不可含空白（新增頁檢查）與特殊字元黑名單
Item2_pic / item2_picvarchar服務圖示檔名，路徑慣例同 code1（itemlogo/<檔名>），大小寫在不同檔案中不一致（Item2_pic vs item2_pic），本質是同一欄位
Use_flagchar/int0 = 使用中／啟用；1 = 未啟用／停用。編輯/新增/列表頁一律只處理 0/1 二元值；code2stopmsg.asp 畫面上多顯示了一個唯讀選項 2=「待上架」，是否真的會出現在資料庫中未經其他檔案佐證（見 D2-11）

沒有 groupid / actionid 欄位 —— 這兩者一律透過 code1 關聯到 TB_GD_RepairCode1_200501 取得，因此本模組幾乎所有查詢都需要 join 這兩張表。

TB_GD_RepairCode3_200501（品牌代碼，僅供關聯檢查）

欄位說明
code1FK → TB_GD_RepairCode1_200501.Code1（與 code2 一樣同時掛在 code1 底下，用於一次 join 三表做檢查）
code2FK → TB_GD_RepairCode2_200501.Code2
Use_flag同上語意，0=啟用中

規則：停用一個 Code2 服務前，必須確認底下沒有任何 Use_flag=0（啟用中）的 Code3 品牌代碼，否則禁止停用（邏輯與 code1 模組「停用前檢查 Code2」完全對稱，只是往下移一層）。

TB_GD_StopServiceMSG_201010 在本模組的用法差異

資料表結構與 code1 模組使用的完全相同（見 code1 規格文件 6.2 節），差異僅在於本模組寫入/查詢時固定使用：

Code1     = 該服務所屬的項目代碼
Code2     = 該服務本身的 Code2（不再是 '0'）
Code3     = '0'（固定，因為本模組不處理品牌層公告）
LinkLevel = 1（固定，代表這是「服務層級」的公告，相對於 code1 模組的 LinkLevel=0「項目層級」）

EndDate 的 +1天／-1天 儲存慣例與 code1 模組完全相同（見 6.3 節），改寫時需同樣還原。

6.3 EndDate 加減一天的邏輯（與 code1 模組相同，必須等價還原）

讀取顯示（code2stopmsg.asp）：
    StopEndDate = DateAdd("d", -1, rsStop("EndDate"))

寫入儲存（code2stopmsg_db.asp）：
    enddate = DateAdd("d", 1, Request("enddate"))

⇒ 資料庫 EndDate 代表「結束隔天 00:00」，畫面上一律呈現「使用者理解的最後生效日」。

6.4 Stored Procedure：SP_GD_StopMsgWork_ONDB_201104（服務層呼叫方式）

定義不在本資料夾內與 code1 模組呼叫的是同一支 SP，但傳入的 Code2／LinkLevel 參數不同：

-- 新增（STOPMSGID = "0" 時）
exec SP_GD_StopMsgWork_ONDB_201104
     'A',
     <actionid>,          -- 來自 code1 記錄的 b.actionid（非 groupid）
     <code1>,
     <code2>,             -- 注意：這裡是實際的 Code2 值，不像 code1 模組固定傳 '0'
     '0',                 -- Code3（固定，本模組不處理品牌層）
     '0','0','',          -- 用途未知，固定傳入
     '1',                 -- 對照 code1 模組固定傳 '0'，這裡固定傳 '1' —— 高度懷疑這個位置就是 LinkLevel 參數
     <msgdata>,
     <begindate>,
     <enddate>,           -- 已 +1 天
     <begintime>,
     <endtime>,
     <stopUseFlag>,
     '0',                 -- StopMsgID（新增時傳 0）
     <Session("Cname")>,
     ''

-- 更新（STOPMSGID <> "0" 時），同上但 Mode='U'，倒數第三個參數改傳既有 STOPMSGID

對照 code1 模組同一位置固定傳 '0'、本模組固定傳 '1'，這強烈暗示該參數就是 SP 內部用來設定 LinkLevel 欄位的值，但因為 SP 定義未提供，仍建議改寫前向 DBA 確認參數簽章。

7. 逐頁詳細規格

頁面 7.1 code2.asp — 服務列表／查詢

輸入參數
mid（groupid，必要）、page、Item_1（項目別下拉，過濾用）、Item_2（服務編號，精確比對）、Item2_name（服務名稱，模糊比對）、wid/fid/sid（僅原樣傳遞）

項目別下拉來源
select * from TB_GD_RepairCode1_200501 where item_1<>99 and use_flag=0 and groupid=<mid> order by Item1_name（排除保留碼 99 的項目，且只列出啟用中的項目）

同 code1：ADO Recordset PageSize=10 靜態分頁
顯示規則

select a.*, b.item_1, b.item1_name as item1_name
from TB_GD_RepairCode2_200501 a, TB_GD_RepairCode1_200501 b
where a.code1 = b.code1
  and b.use_flag = 0
  and b.groupid = <mid>
  [and b.item_1 = '<Item_1>']
  [and a.Item_2 = '<Item_2>']
  [and a.Item2_name like '%<Item2_name>%']
order by b.code1

頁面 7.2 code2add.asp — 新增表單

輸入參數
mid（僅用於查詢下拉選單，沒有被放進表單的隱藏欄位，見 D2-03）
表單欄位
code1(下拉，選擇所屬項目)、Item_2(text,maxlength2)、Item2_name(text,maxlength15)、logo(隱藏，圖片檔名)、Use_flag(radio 0=啟用/1=停用，預設勾選停用)
下拉選單來源
select * from TB_GD_RepairCode1_200501 where use_flag=0 and item_1<>'99' and groupid=<mid> order by code1（只列出啟用中、且不是保留碼99的項目）——此下拉的每個 Option 都寫死加了 selected屬性（見 D2-13，實際效果是永遠選到清單中最後一筆，屬 HTML 撰寫缺陷）
送出目標
POST → code2add_db.asp

必填 Item_2、Item2_name；Item2_name 不可含空白；若 Item_2="99"，跳出確認對話框「服務編號99於前台不顯示!」（僅提示不阻擋）；數字格式檢查(checknumber)同 code1add.asp 一樣被註解掉未執行

處理器 7.3 code2add_db.asp — 新增寫入

輸入參數(POST)
code1、Item_2、Item2_name、logo(→item2_pic)、use_flag
程式缺陷
第8行 response.write Item_2 是除錯用的殘留程式碼，會把 Item_2 的值直接輸出在頁面最前面（HTML 尚未開始輸出前），造成畫面最上方多出一段雜訊文字（見 D2-04）。

第9行的單引號檢查寫的是 Instr(Item_1,"'") 與 Instr(Item1_name,"'") —— 但本檔案從未對 Item_1／Item1_name 賦值（正確應該檢查的是 Item_2／Item2_name）。因為 Classic ASP 對未賦值變數視為空字串，這個檢查形同虛設，永遠不會觸發（見 D2-05）。
業務驗證順序
1) 查是否此 code1 底下已有啟用中的 Item_2=99：select * from TB_GD_RepairCode2_200501 where code1=<code1> and use_flag=0 and item_2=99 → 若有 → alert「此項目已有服務編號為99,無法新增!」並導回
2) 若欲新增的 Item_2="99"：改查此 code1 底下任何啟用中的服務（不限編號）：select * from TB_GD_RepairCode2_200501 where code1=<code1> and use_flag=0 → 若有 → alert「此項目有其他服務且其狀態為啟用!99無法新增!」
3) 若欲新增的 Item_2 不是 99：查是否已有相同 Item_2 且啟用中：select * from TB_GD_RepairCode2_200501 where Item_2='<Item_2>' and code1=<code1> and use_flag=0 → 若有 → alert「服務編號重複且其狀態為啟用!」
4) 通過以上檢查才執行 INSERT
SQL(INSERT)
Insert Into TB_GD_RepairCode2_200501 (code1, Item_2, Item2_name, Item2_pic, use_flag) Values (<code1>,'<Item_2>','<Item2_name>','<item2_pic>',<use_flag>)
結果處理
成功 → alert「新增成功!」→ 導回 Session("url")；失敗分支同 code1 模組，實際不會被觸發（err<>0 判斷失效）

頁面 7.4 code2mod_temp.asp — 編輯／停用中繼表單

輸入參數
Code2(必要)、mod(1=編輯／2=停用)、item_2（列表頁帶來）、Use_flag(mod=2時固定"1")、mid
資料讀取

第12行：actionid=request("mid") —— 變數命名為 actionid，但實際存的是 groupid（mid）的值。
第15行查重複用的 SQL：... and b.actionid='<actionid>' ... —— 拿 groupid 的值去比對 b.actionid（業態代碼）這個完全不同語意的欄位。 對照 code2mod_stop.asp 中同樣命名、同樣賦值的變數，那邊查詢用的卻是 b.groupid=actionid（語意正確）。兩個檔案的變數名稱與賦值方式一模一樣，但比對的欄位不同，其中一個必定是錯的，高度懷疑 code2mod.asp 這裡應該也是 b.groupid 才對。 實際影響：這個查詢是用來檢查「是否有其他啟用中、相同服務編號的記錄」，如果比對錯欄位，這個重複檢查在正常資料下可能永遠查不到任何結果（等於檢查失效），也可能在極少數 actionid 剛好等於某個 groupid 數值時誤判。改寫時建議直接修正為比對 groupid，並在改寫前跟熟悉此系統的人員確認 groupid 與 actionid 的實際數值範圍是否有重疊風險。

8. 商業規則彙整（改寫時的核心行為清單）

  1. 租戶隔離（間接）：Code2 本身無 groupid，所有租戶範圍檢查都必須透過 join 到父層 Code1 的 groupid 完成。
  2. 父項目必須啟用：列表查詢、編輯、暫停訊息設定，都要求所屬 Code1 記錄的 use_flag=0；父項目一旦被停用，其下服務即使原本啟用，也無法再被編輯或設定暫停訊息（只能停用，見下一條）。
  3. 停用服務不檢查父項目狀態：code2mod_stop.asp 本身沒有檢查父 Code1 是否啟用，只檢查子層 Code3 是否啟用，所以就算父項目已停用，服務仍可被個別停用（與規則2的限制範圍不同，改寫時要保留這個不對稱性，除非確認要統一）。
  4. Use_flag 語意：0=啟用（使用中）、1=停用（未啟用），與 code1 模組相同，不要反轉。
  5. 編輯僅限未啟用服務；停用僅限啟用中服務：與 code1 模組相同的互斥顯示規則。
  6. 停用前檢查子層：停用 Code2 前必須確認底下沒有啟用中的 Code3（品牌代碼），否則拒絕（與 code1 模組「停用前檢查 Code2」的規則同構，往下移一層）。
  7. 新增/編輯重複檢查：同一 code1 下，若已存在「相同 Item_2 且 use_flag=0」的服務，禁止新增/編輯為該編號（但編輯頁 code2mod.asp 因 D2-06 缺陷，這個檢查可能比對錯欄位而失效，需在改寫時修正並重新驗證此規則是否真的被正確執行）。
  8. 服務編號 "99" 互斥規則（本模組特有，code1 沒有對應規則）：
    • 同一個項目（code1）底下，「服務編號99」與「其他任何啟用中的服務編號」互斥——只要 99 是啟用中的，就不能再新增/修改出其他啟用中的服務；反過來，只要底下有其他啟用中的服務，也不能新增/修改出啟用中的 99。
    • 此規則在新增（code2add_db.asp）與編輯（code2mod.asp）兩處各自獨立實作了一套相同語意的檢查，改寫時建議合併成一個共用的驗證函式，避免兩處邏輯日後又走偏。
  9. 所屬項目（code1）建立後不可變更：編輯頁（code2mod.asp）的 UPDATE 陳述式沒有更新 code1 欄位，即使表單有帶入該值，實際上不會被用來變更歸屬關係。
  10. 暫停公告固定層級：本模組建立/編輯的暫停公告固定 Code3='0'，疑似對應的 LinkLevel=1（服務層級），對照 code1 模組的 LinkLevel=0（項目層級）。
  11. 暫停公告日期慣例與時間合理性檢查：與 code1 模組完全相同（見 6.3 節與 code1 規格文件相應章節）。
