2GBack 後台改寫架構建議

前提 資料庫（MS SQL Server）與既有資料表 / Stored Procedure 完全不變，本文件只討論應用層（後台程式）該用什麼架構改寫。 內容基於 code1_system_spec.html ~ code5_system_spec.html 五份規格文件的分析結果整理而成。

✅ 已確認技術棧（第7章三個決策點皆採用選項A） 後端語言：ASP.NET Core (C#)　｜　資料存取：Dapper　｜　1G/2G 模組關係：分成兩個獨立 Bounded Context（不強行合併 code1~3 與 code4~5 的資料模型）。 以下內容以此技術棧為準；第7章仍保留 B 選項的比較供未來參考，但目前不採用。

1. 核心原則

  • 資料庫完全不動：延續現有 MS SQL Server、既有資料表（TB_GD_*、TB_ALEX_*）與既有 Stored Procedure（如 SP_GD_StopMsgWork_ONDB_201104）。
  • 把「渲染 HTML／組SQL字串／商業規則」三件事拆開——這是目前 ASP 檔案最大的問題，也是五份規格文件裡列出的多數缺陷（SQL Injection、規則各自為政、變數命名 bug）的根源。
  • 舊系統其實是兩個實質獨立的子系統，新架構要能同時服務兩者，而不是硬併成一個：
    • 1G 主系統（code1~code3，TB_GD_*，對應舊連線 conn/conn0）
    • 2G 票務中心（code4~code5，TB_ALEX_*，對應舊連線 conn3，外加寫入 conn 的稽核 log）

2. 技術選型建議

層採用技術理由
後端框架✅ ASP.NET Core (C#)現有環境是 Windows/IIS/MSSQL，驅動與部署摩擦最小；團隊從 VBScript 過渡到 C# 學習曲線較平緩
資料存取✅ Dapper輕量、貼近原生SQL好對照舊查詢，支援參數化查詢與現有 Stored Procedure 呼叫，不需要資料庫改動
前端React 或 Vue 的 SPA，呼叫後端 REST API直接把已完成的 UI/UX 原型（code1、code2）接上真實 API
認證沿用 MSSQL 帳密表，改用 JWT 或 Cookie Session 簽發，取代舊有的 Session("Cname")／chk_session2.asp租戶（groupid）綁定登入身分，不再信任網址參數（修正各模組「D-04越權風險」類缺陷）

備選方案若團隊更偏好 JS/TS 全端，可用 Node.js + Fastify/Express + Prisma 取代 ASP.NET Core，一樣能接同一個 MSSQL；主要代價是 Windows 整合驗證與既有 Session 機制要多花力氣搬遷。

4. 關鍵設計決策（對應規格文件發現的問題）

  1. 狀態機顯式化：Use_flag 0/1(/2待上架) 改成具名 enum（Active/Inactive/PendingListing），在 Repository 層做資料庫值↔enum 的轉換，Service 層不再看到魔術數字。
  2. 租戶範圍強制檢查：所有 Repository 查詢都要求傳入登入者的 groupId，不再讓前端網址參數決定範圍。
  3. 保留碼（99）互斥規則抽成共用函式：Code1~Code5 各模組都有類似但實作深度不一的99規則（code1只警告、code2真的互斥、code3~code5各有缺陷），先跟需求方確認正確行為後，寫成一個共用的 assertReservedCodeExclusivity()。
  4. 雙資料庫寫入包成一個 Unit of Work：code4/code5 模組會同時寫 conn3（主檔）和 conn（稽核log），改寫後用交易或至少確保失敗時有重試/補償，不要像現在「log失敗使用者也看不出來」。
  5. 驗證規則前後端共用一份定義：如 Zod/FluentValidation，取代目前五個模組各自複製貼上的 JS 黑名單字元檢查。

5. 現有模組對照表

舊模組資料表新 Service備註
code1（項目管理）TB_GD_RepairCode1_200501ItemService最單純、依賴最少，建議第一個遷移
code2（服務管理）TB_GD_RepairCode2_200501ServiceService含保留碼99雙向互斥規則
code3（品牌管理）TB_GD_RepairCode3_200501BrandService含1支孤兒處理器，遷移前需確認規則取捨
code4（地區管理，2G）TB_ALEX_RepairCode4_200601RegionService三態狀態機、1G/2G欄位分工
code5（類型管理，2G）TB_ALEX_RepairCode5_200601TypeService下接真實商品/票券資料表

6. 遷移策略

  • 按模組垂直切，不要整包重寫：先做 code1（項目管理），驗證整套新架構（認證、分層、與舊DB共存）可行，再依樣套用到 code2~code5。
  • 新舊系統並存過渡期：新 API 與舊 ASP 頁面同時指向同一個資料庫，舊頁面逐步下線，降低一次性風險。
  • 1G 與 2G 分成兩個 Bounded Context，共用同一套認證/租戶機制，但資料模型與 Service 層分開維護，不要為了「看起來像同一套代碼」而勉強合併 Code1~3 和 Code4~5。
