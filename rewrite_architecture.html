2GBack 後台改寫架構建議

前提 資料庫（MS SQL Server）與既有資料表 / Stored Procedure 完全不變，本文件只討論應用層（後台程式）該用什麼架構改寫。 內容基於 code1_system_spec.html ~ code5_system_spec.html 五份規格文件的分析結果整理而成。

✅ 已確認技術棧（第7章三個決策點皆採用選項A） 後端語言：ASP.NET Core (C#)　｜　資料存取：Dapper　｜　1G/2G 模組關係：分成兩個獨立 Bounded Context（不強行合併 code1~3 與 code4~5 的資料模型）。 以下內容以此技術棧為準；第7章仍保留 B 選項的比較供未來參考，但目前不採用。

⚠️ 資料庫表格的資料與格式一律不可異動 不只是「繼續用 MS SQL Server」這麼寬鬆的意思——TB_GD_*、TB_ALEX_* 等既有資料表的欄位名稱、欄位型態、既有資料內容與既有格式慣例（例如 Use_flag 的 0/1/2 數值、EndDate 存檔時 +1 天的慣例、groupid 補零方式等）都必須原封不動保留，不可因為改寫後台就順手「順便」調整資料庫 schema 或修改既有資料去配合新程式比較好寫。 新系統的 Repository 層／Service 層要負責把這些舊有、有時反直覺的資料格式，轉換成應用層看得懂的乾淨模型（例如 6.1 節提到的 Use_flag enum 轉換），轉換邏輯只能存在於應用層，不能透過改資料庫來讓問題「消失」。若真的發現某個欄位格式已經造成嚴重維護負擔，需要先跟熟悉舊系統與其他仍在使用同一批資料表的系統（例如舊 ASP 頁面尚未下線期間）的相關人員確認後才能討論異動，不能自行決定。

⚠️ v2 發現：code1~code3 已遷移到「2G票務中心」資料庫，1G/2G分界需重新確認 撰寫本文件初版時，code1~code3 使用 TB_GD_* 資料表（對應本文件原本定義的「1G主系統」）。之後追蹤 code1_system_spec.html／code2_system_spec.html／code3_system_spec.html 的 v2 改版才發現：這三個模組的 ASP 原始碼已經改接 TB_ALEX_RepairCode1~3_200501（經 conn3，ALEX_TICKET_200602），與 code4/code5 共用同一套「2G票務中心」schema、三態狀態機（啟用/停用/待上架）、預售期間欄位與雙資料庫稽核寫入。 這代表本文件第1章與第5章原本「code1~3是1G（TB_GD_*）、code4~5是2G（TB_ALEX_*）」的分界描述已經過時，已於下方對應章節更新；但目前尚未確認 TB_GD_RepairCode1~3_200501 這些舊表是否還有其他系統在讀寫——若還有，1G系統本身可能仍存在，只是code1~3後台改由新架構代管，改寫時務必先與熟悉舊系統的人員確認，不能自行假設舊表已可廢棄。

⚠️ 與已建置的 2GBack-api 試作後端的落差 目前已實際建置的 code1/code2 REST API 試作專案（私有 repo 2GBack-api），是在發現上述 v2 遷移之前依照舊架構建立的，其連線資訊指向 GD_SALES_BARK_200412 資料庫的 TB_GD_RepairCode1/2_200501 表（即v1架構）。 若之後要延續、修正或擴充該試作專案，需要先與需求方確認：正式改寫究竟該對接 GD_SALES_BARK_200412（v1舊表）還是 ALEX_TICKET_200602 的 TB_ALEX_RepairCode1/2_200501（目前ASP原始碼實際在用的v2新表）——這是本文件目前唯一尚待確認、可能影響既有試作程式碼是否需要重新對接的開放問題。

1. 核心原則

  • 資料庫完全不動，資料與格式也一律不可異動：延續現有 MS SQL Server、既有資料表（TB_GD_*、TB_ALEX_*）與既有 Stored Procedure（如 SP_GD_StopMsgWork_ONDB_201104）——不只是換一套程式接同一顆資料庫而已，欄位結構、既有資料內容、既有的資料格式慣例（Use_flag 數值、日期 +1 天慣例等）都要原樣保留，不可為了讓新程式好寫而修改 schema 或動既有資料。
  • 把「渲染 HTML／組SQL字串／商業規則」三件事拆開——這是目前 ASP 檔案最大的問題，也是五份規格文件裡列出的多數缺陷（SQL Injection、規則各自為政、變數命名 bug）的根源。
  • ⚠️（v2更新）原「1G/2G以模組編號分界」的假設已過時：code1~code3 的 ASP 原始碼經追蹤後已確認全部改接 TB_ALEX_*（經 conn3，ALEX_TICKET_200602），與 code4~code5 共用同一套「2G票務中心」schema、三態狀態機與稽核log機制，不再是「code1~3用TB_GD_*」。目前 code1~code5 在應用層看到的實際主資料表現況為：
    • 2G 票務中心（現況，code1~code5 皆在此）：TB_ALEX_RepairCode1~5_*，經 conn3（ALEX_TICKET_200602），外加寫入 conn 的稽核 log（TB_GD_UserClick_Log_200507）
    • 舊 TB_GD_RepairCode1~3_* 表（GD_SALES_BARK_200412）：現行 code1~3 的 ASP 頁面已不再讀寫，但尚未確認是否有其他系統仍在使用——不可假設可廢棄，需求方確認前先視為仍存在的獨立資料集合
    第7章「1G/2G合併程度」決策點的原始理由（避免混淆TB_GD與TB_ALEX）因此需要重新檢視，目前傾向：新後端統一對接 ALEX_TICKET_200602／conn3 這一套2G票務中心schema即可，不需要再刻意維持兩個Bounded Context——但這牽動已建置的 2GBack-api 試作專案（見上方callout），需要與需求方確認後才能定案，本文件先如實記錄此開放問題。

2. 技術選型建議

層採用技術理由
後端框架✅ ASP.NET Core (C#)現有環境是 Windows/IIS/MSSQL，驅動與部署摩擦最小；團隊從 VBScript 過渡到 C# 學習曲線較平緩
資料存取✅ Dapper輕量、貼近原生SQL好對照舊查詢，支援參數化查詢與現有 Stored Procedure 呼叫，不需要資料庫改動
前端React 或 Vue 的 SPA，呼叫後端 REST API直接把已完成的 UI/UX 原型（code1、code2）接上真實 API
認證沿用 MSSQL 帳密表，改用 JWT 或 Cookie Session 簽發，取代舊有的 Session("Cname")／chk_session2.asp租戶（groupid）綁定登入身分，不再信任網址參數（修正各模組「D-04越權風險」類缺陷）

備選方案若團隊更偏好 JS/TS 全端，可用 Node.js + Fastify/Express + Prisma 取代 ASP.NET Core，一樣能接同一個 MSSQL；主要代價是 Windows 整合驗證與既有 Session 機制要多花力氣搬遷。

4. 關鍵設計決策（對應規格文件發現的問題）

  1. 狀態機顯式化：Use_flag 0/1(/2待上架) 改成具名 enum（Active/Inactive/PendingListing），在 Repository 層做資料庫值↔enum 的轉換，Service 層不再看到魔術數字。
  2. 租戶範圍強制檢查：所有 Repository 查詢都要求傳入登入者的 groupId，不再讓前端網址參數決定範圍。
  3. 保留碼（99）互斥規則抽成共用函式：Code1~Code5 各模組都有類似但實作深度不一的99規則（code1只警告、code2真的互斥、code3~code5各有缺陷），先跟需求方確認正確行為後，寫成一個共用的 assertReservedCodeExclusivity()。
  4. 雙資料庫寫入包成一個 Unit of Work：code4/code5 模組會同時寫 conn3（主檔）和 conn（稽核log），改寫後用交易或至少確保失敗時有重試/補償，不要像現在「log失敗使用者也看不出來」。
  5. 驗證規則前後端共用一份定義：如 Zod/FluentValidation，取代目前五個模組各自複製貼上的 JS 黑名單字元檢查。

6. 遷移策略

  • 按模組垂直切，不要整包重寫：先做 code1（項目管理），驗證整套新架構（認證、分層、與舊DB共存）可行，再依樣套用到 code2~code5。
  • 新舊系統並存過渡期：新 API 與舊 ASP 頁面同時指向同一個資料庫，舊頁面逐步下線，降低一次性風險。
  • （v2更新）1G/2G Bounded Context 分界需重新確認：原建議是「1G（code1~3）與2G（code4~5）分成兩個獨立Bounded Context」，但既然code1~3已證實改接與code4~5相同的 ALEX_TICKET_200602 schema，這個分界的原始依據已不成立。除非需求方確認舊TB_GD_RepairCode1~3_*表仍有其他系統在用（代表1G系統本身仍存在，只是不再由code1~3後台代管），否則新架構可考慮以單一Bounded Context處理code1~5，降低不必要的重複建模成本。
  • 試作進度與v2發現不同步，需要對齊：已建置的 2GBack-api（code1/code2）目前對接的是v1舊表 GD_SALES_BARK_200412；在往code3~code5擴充或正式投產前，應先與需求方確認是否要把 2GBack-api 也改接 ALEX_TICKET_200602／TB_ALEX_RepairCode1/2_200501，以符合目前ASP原始碼實際在用的架構，避免新舊系統各自對接不同資料表造成資料不一致。

7. 風險與取捨

以下三個決策點皆已確認採用選項A（打勾標示）；選項B僅保留供未來若情況改變時參考，目前不採用。

決策點選A選B取捨
後端語言✅ ASP.NET Core (C#)Node.js + TypeScriptA對現有Windows/IIS環境摩擦最小；B前端後端同語言、社群資源多，但Session/Windows驗證要多搬
資料存取✅ DapperEF CoreA輕量、貼近原生SQL好對照舊查詢；B有變更追蹤/關聯載入等進階功能，但學習曲線較高
1G/2G合併程度✅ 分成兩個獨立Bounded Context（⚠️前提已變，見下方說明）強行合併成一套模型A維護清晰但要多寫一些共用邏輯；B短期看起來簡單，長期容易再現「TB_GD vs TB_ALEX」這種混淆

⚠️「1G/2G合併程度」決策的前提已被v2發現推翻，需要重新確認此決策當初是依據「code1~3用TB_GD_*是1G、code4~5用TB_ALEX_*是2G」畫分。現已證實code1~3也改接TB_ALEX_*／ALEX_TICKET_200602，五個模組實際上共用同一套schema，「兩個獨立Bounded Context」的原始理由不再成立。是否仍要維持兩個Context（例如因為業務語意上1G/2G仍是兩套產品線，即使資料庫共用）、或改採單一Bounded Context，屬於需要與需求方重新確認的決策，本文件先誠實記錄、不預先變更選項A的勾選狀態。
